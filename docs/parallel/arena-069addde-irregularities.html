#findingevidencedisposition
1labels.tif and existing_faults.tif are byte-identical. Both files hash to 7ba308ccdc4418b31a178f4f1ef21aaa6e152e4028f2f6f64b01f7eb25ae4093 (recorded in evidence/data_sha256.txt). They are distributed as separate artifacts on the competition data page. Flagged. The pipeline reads only labels.tif. If the two are meant to differ, any lane that treats them as distinct is silently using one file twice. Needs a question on the forum.
2One registry raster could not be fetched. scripts/fetch_registry.py returned HTTP 404 for gems48_h59_cover_ds_belief_02296; 21 of 22 entries verified. Excluded from the gate and reported. The uniqueness gate therefore covers 21 rasters, not 22.
3Spearman correlation is degenerate on binary masks. Over the union of two binary supports both vectors are constant 1, so rho is undefined. A naive implementation returned 0.0 for two identical rasters — which would have passed an exact duplicate through the lane-drift gate. Fixed in src/gems63/uniqueness.py: rank over the full grid, where Spearman on binary masks is the phi coefficient. Regression test test_identical_raster_is_flagged_as_duplicate.
4The cluster bootstrap always returned None. It matched truth pixels against the withheld segment's catalogue coordinates. In this lane the truth is a laterally displaced copy, so the two never coincide, no segment was ever kept, and the routine returned no interval at all. Fixed in src/gems63/holdout.py: resample connected components of the truth. Regression test test_cluster_bootstrap_returns_an_interval.
5expected_kernel_weight was wrong by ~0.2 absolute. The telescoping sum used (1 - S_j) where the algebra requires S_j. It reported 0.847 where Monte-Carlo and a hand enumeration both give 0.65552 at pi = 0.2. Fixed in src/gems63/metric.py; the hand-enumerated value is now an assertion, and the closed form is checked against 6000 Monte-Carlo draws at three pi levels.
6The published worked example is 0.602652, not 0.60. 3.00 / (3.00 + 0.2×1.89 + 0.8×2.00) = 3.00 / 4.978 = 0.6026516. The competition page displays "0.60". Not a defect — a rounding on the page. Both facts are asserted in test_published_tversky_example so the discrepancy is never re-litigated.
7Integer rounding pushed world displacements past the calibrated cap. Rounding a 4 px disc vector to integers produced displacements of 4.47 px = 447 m, above the 400 m the calibration is based on. Fixed in src/gems63/worlds.py: vectors are shrunk back inside the disc. Verified: maximum observed displacement over 12 worlds is exactly 4.00 px.
8A sibling tool has an import that cannot resolve. In sibling 62GEMSDOE, src/gems62/holdout.py does from .metric import dti_components, but that repo's src/gems62/metric.py defines dti_binary and no dti_components. Not fixed here — it is another repository's file and the brief forbids a private fork of a shared tool. Reported instead. This repository implements its own gems63_rs.metric with an independent test suite.
9The competition data is not reachable from this sandbox. HTTP 000 from www.drivendata.org and usgs.gov; the data page requires login in any case. The feature stack was recovered as five split parts committed to sibling repositories and reassembled here (sha256 4371c82e3b8339b807bdffcf4ef59a225520fe2988d521be208ae33743123bc5, 418,912,844 bytes, 19 bands, EPSG:32611, 3292×3730). Provenance is recorded in data/README.md. This is a second-hand copy, not a download from the organizer, and is flagged as such.
10The holdout cannot validate this lane's mechanism on its own. A hide-and-recover holdout that withholds whole segments produces truth that is, by construction, not adjacent to the visible catalogue. A first run scored an offset ribbon at 0.0096 against it. Structural, not a bug. The world generator therefore spans the share of truth that is displaced catalogue geometry (phi) from 0.15 to 0.95, and the CVaR objective is tail-penalised over that whole range. Stated plainly: the holdout number is a conditional statement about a proxy truth, not a measurement of the real target.
